# Git Workflow (Git Flow)

This is the binding policy for how code moves from an idea to a release. It applies to the maintainer, to AI coding agents, and to every tool. Decision record: [ADR-0011](../adr/0011-git-flow-merge-commits.md). Agent-facing summary: [AGENTS.md](../../AGENTS.md).

## 1. Branches

| Branch | Purpose | Who may change it | How |
|---|---|---|---|
| `main` | Released code only. Each release is a merge commit of `dev`, and that merge commit carries the version tag. | Nobody directly | `scripts/release.sh publish` (merge commit, human only) |
| `dev` | Integration branch. Always green. | Nobody directly (one exception below) | `scripts/land.sh` (merge commit) |
| `feature/<name>` | New functionality | Author | Branch from `dev`, land into `dev` |
| `bugfix/<name>` | Fix for a defect found on `dev` | Author | Branch from `dev`, land into `dev` |
| `docs/<name>`, `chore/<name>`, `spike/<name>` | Docs, maintenance, time-boxed investigations | Author | Branch from `dev`, land into `dev` |
| `release/<X.Y.Z>` | Prepares a release (version and changelog commit) | Anyone | `scripts/release.sh prepare` branches from `dev`; land it into `dev`; the human then publishes `dev` to `main` |
| `hotfix/<name>` | Urgent fix for a released version | Author | Branch from `main`; `scripts/land.sh hotfix/<name> --into main`; the human tags it; back-merge `main` into `dev` |

Step-by-step commands for all of this are in the [runbook](runbook.md).

Names are lowercase kebab-case after the prefix: `feature/timer-tool`, `bugfix/opus-underrun`. Include an issue number when one exists (`feature/42-timer-tool`). Enforced by the `pre-commit` hook and the agent guard.

## 2. The rules

1. **Never commit to `main`.** Not even a typo.
2. **Do not commit to `dev`.** The only exception is **one** tiny change: a single commit of at most **10 changed lines in at most 2 files**, with nothing else unlanded on `dev`. Anything else goes on a branch.
3. **Nothing reaches `dev` unless every gate passes** (section 5). Nothing reaches `main` unless the release gate passes (section 6).
4. **Merge commits, no squash, no PRs between the maintainer and their pair programmer.** History keeps the real commits. (External contributors use pull requests; section 8.)
5. **Commit like a human, early and often.** Small logical commits that each make sense on their own, with tests and docs in the same branch. No "WIP" or "fix stuff" commits; amend or reorganise them before landing.
6. **Never rewrite shared history.** No force-pushes. Rebasing your own unpublished branch is fine.
7. **Commits are authored by the human only** (section 4).

## 3. Commit messages

[Conventional Commits 1.0](https://www.conventionalcommits.org/), enforced on every commit (not just the merge) by the `commit-msg` hook, by `scripts/land.sh`, and by CI.

```
<type>(<scope>)<!>: <imperative summary, <= 72 chars, no trailing period>

<body: what and why, wrapped at ~80 columns; not how>

Refs: REQ-TMR-001, REQ-TMR-004
BREAKING CHANGE: <description, if any>
```

- **Types:** `feat`, `fix`, `docs`, `spec`, `refactor`, `perf`, `test`, `build`, `ci`, `chore`, `revert`.
- **Scopes (suggested):** `core`, `protocol`, `satellite`, `audio`, `wake`, `session`, `stt`, `tts`, `llm`, `tools`, `mcp`, `sched`, `inbox`, `http`, `ui`, `store`, `config`, `budget`, `deps`, `release`.
- Imperative mood ("add timer tool", not "added"). Explain *why* in the body. Reference requirement IDs with `Refs:`.
- A `!` after the type/scope, or a `BREAKING CHANGE:` footer, marks a breaking change.
- Merge commits are generated by `scripts/land.sh` ("Merge feature/x into dev") and are exempt.

Types drive the changelog and the next version (section 7).

## 4. Identity and attribution

- All commits, merges, and tags are authored by the configured human identity. The repository-local git config is set to the maintainer's name and email.
- **AI agents never author or co-author commits.** No `Co-Authored-By` trailers, no "Generated with ..." lines, no AI emoji signatures, no AI author or committer identities. This is checked by the agent guard, the `commit-msg` hook, and CI (`commits` job, author and committer identities included).
- Changing `user.name`, `user.email`, `user.signingkey`, or using `--author` is blocked for agents.
- **Signing:** commit and tag signing is recommended; it is enabled and made a server-side requirement once the maintainer has signing keys configured. Until then tags are annotated and unsigned.

## 5. The path into `dev`

```
git switch dev && git pull        # start from an up-to-date dev
git switch -c feature/timer-tool  # work on a branch
# ... commit early and often (hooks run) ...
git merge dev                     # make the branch contain dev (resolve conflicts here)
scripts/land.sh feature/timer-tool
```

`scripts/land.sh <branch>`:
1. Requires a clean working tree and that the branch **contains `dev`**, so the merge commit's tree is exactly what was tested.
2. Runs **every gate** on the branch tip (`scripts/check.sh`): formatting, lint and type-check, unit/integration tests, documentation checks, commit-message and identity checks, shell checks, and dependency policy.
3. Creates the merge commit on `dev` (`git merge --no-ff`).
4. **With a remote:** pushes that exact commit to a candidate ref `ci/dev/<sha>`, waits for the `gate` job to pass, and only then pushes it to `dev` (the server accepts it because that SHA already has a passing check). On failure `dev` is reset locally and nothing is published.
5. Deletes the merged branch.

The tiny-commit exception: make the single commit on `dev` (the `pre-commit` hook verifies the size), then run `scripts/land.sh --tiny`.

Required gates (all of them, with no exceptions):

| Gate | What | Tool |
|---|---|---|
| Formatting | Code is formatted | `cargo fmt --check` |
| Lint and type-check | No warnings | `cargo clippy -D warnings` |
| Unit and integration tests | All pass | `cargo test` |
| Dependency policy | Licences and advisories | `cargo deny` |
| Docs | Links resolve; requirement IDs unique | `scripts/check-docs.sh` |
| Commits | Conventional; human-only identities | `scripts/check-commit-msg.sh` |
| Scripts | Syntax and shellcheck | `bash -n`, `shellcheck` |
| Budget (from TASK-003) | Binary size and RSS within gates | budget gate |

Rust gates activate automatically when `Cargo.toml` exists; if `Cargo.toml` exists and `cargo` is missing, the gate fails (it never silently passes).

## 6. Releases

A release is three steps: **prepare**, **land**, **publish**.

```
git switch dev
scripts/release.sh prepare          # branches release/X.Y.Z from dev; computes the next SemVer from the commits;
                                    # regenerates CHANGELOG.md with git-cliff; commits "chore(release): vX.Y.Z"
scripts/land.sh release/X.Y.Z       # lands the release commit into dev like any other branch
scripts/release.sh publish X.Y.Z    # HUMAN ONLY: merges dev into main with a merge commit, tags that commit
```

`publish` runs the release gate, asks the human to type the tag to confirm (it needs an interactive terminal, so agents cannot run it), merges `dev` into `main` with a **merge commit** pushed only after CI passes on that exact commit, **tags the merge commit** `vX.Y.Z`, and pushes the tag. The tag triggers the `release` workflow.

Release gate (beyond the normal gates): `CHANGELOG.md` has an entry for the version, the working tree is clean, and the Cargo workspace version matches. The `release` workflow then builds the artifacts, **ships `CHANGELOG.md` in the release package**, and publishes the GitHub Release with notes generated from the commits. From v1.0 the changelog is also embedded in the build and shown in the UI "About" page (REQ-CFG-013).

`main` only ever receives merge commits (`dev` into `main` for a release, a `hotfix/*` branch into `main` for a hotfix), and each is pushed only after CI has passed on that exact commit, so every commit on `main` has passed the `gate`. The version tag points at the `Merge dev into main (release vX.Y.Z)` commit.

**Hotfix:** branch `hotfix/<name>` from `main`, fix and regenerate the changelog for the patch version, land it into `main` (`scripts/land.sh hotfix/<name> --into main`), then the human runs `scripts/release.sh tag X.Y.Z`. Finally back-merge `main` into `dev` on a `chore/back-merge-vX.Y.Z` branch. Commands: [runbook section 8](runbook.md#8-hotfix-urgent-fix-to-a-released-version).

## 7. Versioning and tags

[Semantic Versioning 2.0](https://semver.org). Tags are annotated, named `vMAJOR.MINOR.PATCH` (with `-alpha.N`, `-beta.N`, `-rc.N` pre-releases), and created only by `scripts/release.sh` on `main`. The satellite protocol has its own version, tagged `protocol-vMAJOR.MINOR`.

The next version is derived from Conventional Commits since the last tag:

| Commits since last release | Bump |
|---|---|
| any `BREAKING CHANGE` / `!` | MAJOR (while `0.x`: MINOR) |
| any `feat` | MINOR |
| only `fix`, `perf`, etc. | PATCH |

Planned mapping to roadmap milestones (minor version per milestone, patch for fixes):

| Milestone | Release |
|---|---|
| M1 walking skeleton | `v0.1.0` |
| M2a / M2b agent inbox | `v0.2.0` / `v0.3.0` |
| M3 time and local intelligence | `v0.4.0` |
| M4 web UI | `v0.5.0` |
| M5 tools and music | `v0.6.0` |
| M6 hardening and Raspberry Pi | `v1.0.0-rc.1`, then `v1.0.0` |

## 8. External contributors

Contributors without write access fork the repository and open a **pull request against `dev`**. CI (`gate`) must pass; the maintainer reviews and merges in the GitHub UI with **Create a merge commit**. The same commit conventions apply to every commit in the PR. The maintainer and their agents do not open PRs for their own work.

The two paths coexist: the maintainer's work reaches `dev` through `scripts/land.sh` (candidate ref, CI, publish), outside contributors' work through pull requests, and both need a passing `gate`.

**If the project grows,** these adjustments are planned (settings, not new machinery; see [repo-settings.md](repo-settings.md)):
- A pull-request rule on `dev` (one approving review) for everyone except the maintainer, who bypasses it because the landing script is their path.
- GitHub's "require approval for first-time contributors" before workflows run on a fork PR.
- DCO sign-off enforcement and a `CODEOWNERS` file (both dormant today; see [SDLC section 13](sdlc.md#13-proportionality-solo-maintainer-mode)).
- Reconsider squash-merging **outside** PRs only. Requiring Conventional Commits on every contributor commit is friction for newcomers; squashing with a Conventional PR title keeps the changelog clean. If adopted, the `commits` CI check validates the PR title for PR events and every commit for pushes.

## 9. Enforcement layers

No single layer is trusted alone.

| Layer | Covers | Where |
|---|---|---|
| Agent guard | Claude Code: blocks violating git/gh commands before they run | `.claude/hooks/guard-git.sh`, `.claude/settings.json` |
| Agent instructions | All AI tools | `AGENTS.md`, `CLAUDE.md` |
| Local git hooks | Every tool using git: branch names, protected branches, commit messages, fast checks | `.githooks/`, installed by `scripts/setup.sh` as stubs in `.git/hooks`. The stubs fail closed on `main`, which has no `.githooks/` until the first release. |
| Landing scripts | The only path into `dev`/`main`; runs all gates | `scripts/land.sh`, `scripts/release.sh` |
| CI | Re-verifies everything on every branch and candidate ref | `.github/workflows/ci.yml` (`gate`) |
| Server rulesets | `main`/`dev` need a passing `gate` on the pushed SHA; no force-push or deletion; tags protected | [repo-settings.md](repo-settings.md) |

Local hooks can be bypassed by someone determined; the server rules and CI cannot. That is why both exist.

## 10. Repository hygiene

- Never commit secrets. API keys live in git-ignored config; the repo ships `config.example.toml` only. Secret scanning is enabled on GitHub.
- Do not commit build outputs, model blobs over 1 MB, or audio fixtures over 500 KB without discussion (Git LFS for approved large fixtures).
- `Cargo.lock` is committed (this is an application).
- Line endings are LF via `.gitattributes` and `.editorconfig`.
- Delete merged branches (the landing script does).
